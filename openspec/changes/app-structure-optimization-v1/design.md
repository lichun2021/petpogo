## Context

见 `proposal.md - Why`。本设计关注一个跨页面的架构命题：**设备/宠物异常事件从产生到展示的全链路数据流**。当前代码里这条链路是半成品——`message_page.dart:1197` 已能解析 `fence_alert` 这种 IM 自定义消息，`sql/init.sql` 已有 `t_fence_alert` 表，`push_service.dart` 已集成极光推送，但三者未串成完整通路，且各处对"数据从哪来"的认知不一致（曾误把腾讯 IM 当事件通知通道、误把历史事件当 PeerApi 直查）。

三套后端的真实分工是本设计的出发点：

| 后端 | 角色 | 前端客户端 |
|---|---|---|
| PeerApi（iPet 网关，不在本仓库） | 设备事件源 + 实时设备状态 | `PeerApiClient`（token 头、form-encoding） |
| 业务后端 `petpogo-server`（独立仓库） | 事件落库 + 推送分发 + 历史查询 | `ApiClient`（Bearer jwt、JSON） |
| 腾讯 IM（外部 SaaS） | 纯社交通讯（私信/好友/点赞评论） | 腾讯 IM SDK |

## Goals / Non-Goals

**Goals:**
- 明确"当前状态"与"历史事件"的数据源分流准则，避免实施时再次混淆。
- 串通系统通知链路的三段职责，让前端能独立于 PeerApi 推进。
- 锁定首页"我的宠物"区块的分阶段落地路径（无依赖先行、等接口接入）。
- 确定寻宠导航、社区分类联动等具体改动的技术选型。

**Non-Goals:**
- 不设计业务后端 `petpogo-server` 的接口字段（由后端仓库定义）。
- 不实现健康报告页（依赖项圈行为分析模型，本轮仅预留入口）。
- 不重构腾讯 IM 的社交通讯职责（`fence_alert` 历史借用保持现状，不扩展）。
- 不决定机器人/萌宠圈页面（已开发，本轮不动）。

## Decisions

### 决策 1：数据源分流准则——当前状态 vs 历史事件

```
当前状态 (实时快照) ──→ PeerApi
  "豆包此刻在围栏内吗？" / "电量多少？"
  问产生数据的源头

历史事件 (流水记录) ──→ 业务后端
  "豆包昨天越界过几次？" / "上周离线告警"
  问存数据的地方
```

**依据**：`t_fence_alert` 表结构（`sql/init.sql:111-123`）是事件流水（`id/fence_id/device_id/user_id/distance/created_at`），无"当前状态"字段；`DeviceModel.isOnline` 是业务后端维护的实时属性，是当前状态但已就绪的特例。围栏状态、电量在业务后端无对应存储，必须问 PeerApi。

**备选方案与拒绝理由**：
- *"全部走 PeerApi"*：拒绝。历史告警需要按用户分页、已读状态、跨设备聚合，PeerApi 是设备维度查询，不适合做用户维度历史；且 `t_fence_alert` 已建，业务后端落库是既定方向。
- *"全部走业务后端"*：拒绝。当前状态若由业务后端缓存，存在与 PeerApi 真值不一致的风险，且业务后端目前没有 `device_status` 这类当前状态表。

### 决策 2：系统通知链路三段架构

```
PeerApi (iPet, 事件源)
   │ webhook 回调
   ▼
业务后端 petpogo-server (中转 + 存储 + 推送)
   ① 落库: t_fence_alert (越界, 已建)
           离线/低电表 (待建, 结构参照 t_fence_alert)
   ② 推送: 调极光 REST API → 按 alias=userId 推
   ③ 开接口: GET /sdkapi/device-event/list (分页+类型过滤)
            POST /sdkapi/device-event/read (标记已读)
   │
   ├─→ 极光推送 (JPush, 已集成)
   │     ↓ extras: { type, device_mac, pet_id }
   │     ↓ push_service.dart 解析 → 路由跳转
   │
   ▼
前端 App (展示)
   系统通知列表页: 调业务后端接口 (不直接调 PeerApi)
   铃铛入口: 首页(新增) + 我的页(修复) → 都指消息页
```

**关键点**：前端**不直接调 PeerApi 拿事件历史**。这跟决策 1 的"历史事件 → 业务后端"一致。腾讯 IM **不参与**设备事件通知（`fence_alert` 在 IM 里的解析是历史借用，本次不扩展其作为事件通知通道的角色）。

**备选方案与拒绝理由**：
- *"实时层走 IM 自定义消息"*：拒绝。腾讯 IM 是社交通讯服务，事件通知混入会污染会话列表；且 IM 漫游期（默认 7 天）受腾讯规则约束，不适合做事件持久化。极光推送是独立通道，已集成且带跳转链路，是事件通知的正确载体。
- *"前端直接调 PeerApi 拿历史"*：拒绝。违背 AGENTS.md 的分层约定（硬件网关 vs 业务后端），且 PeerApi 无用户维度的历史聚合能力。

### 决策 3：前端独立于 PeerApi 推进

系统通知列表页和首页"我的宠物"区块都依赖尚未就绪的接口（业务后端查询接口、PeerApi 围栏/电量状态接口）。采用**预留接入点**策略，让前端不阻塞：

```
阶段 1 (无依赖, 立即可做):
  - 系统通知列表页 UI + 空状态 + Repository 壳 (方法签名已定, 实现先返回 mock/空)
  - "我的宠物"区块 UI, 在线/离线用 DeviceModel.isOnline
    围栏/低电显示 "-" 或 "未知"
  - 铃铛跳转、AI 积分提示、文案修复、社区分类联动等纯 UI/现成数据改动

阶段 2 (等业务后端接口):
  - 接 /sdkapi/device-event/list → 系统通知列表页真实数据
  - 接已读回写接口

阶段 3 (等 PeerApi 实时状态组, "马上实现"):
  - 接电量接口 → "我的宠物"低电状态
  - 接围栏状态接口 → "我的宠物"围栏内/越界
```

**Repository 预留形式**：新增 `DeviceEventRepository`，方法签名固定，实现先用 mock。接口好后只改 repository 一个文件，不影响 UI 和路由。

### 决策 4：寻宠导航——url_launcher 方案 C

```
触发: pet_location_page.dart 底部操作区新增"🧭 寻宠导航"按钮
前置: _gcjLatLng != null (无定位则禁用)

坐标系 (两套都在手, 无需新增转换):
  _gcjLatLng (GCJ02)  → 高德/百度
  _position  (WGS84)  → Apple Maps / Google Maps

优先级链 (canLaunch 逐个探测):
  1. androidamap://navi?... / iosamap://navi?... (高德)
  2. baidumap://map/direction?... (百度)
  3. comgooglemaps://?... (Google Maps)
  4. maps://?... / geo:0,0?q=lat,lng (Apple/系统)
  全部失败 → Toast "未找到地图 App"
```

**依据**：`url_launcher: ^6.3.0` 已在 `pubspec.yaml`，`pet_mood_section.dart:169` 已有 `launchUrl` 用法先例。现有 `flutter_map` + 高德瓦片方案不引入高德 SDK，方案 C 与现状架构一致，零新依赖。

**备选方案与拒绝理由**：
- *方案 A（URL scheme 唤起高德 App，无降级）*：拒绝。覆盖面不全，未装高德的用户无处可去。
- *方案 B（引入高德 SDK 内嵌导航）*：拒绝。集成成本高，与现有 `flutter_map` 架构冲突。

### 决策 5：社区分类联动——前后端同步

社区页分类标签筛选与发布动态页分类选项是**前后联动**关系，必须同步开发，单独上线任一端均无效果。后端 `category` 字段已就绪。

- 发布动态页：发帖时传 `category` 值（猫/狗/其他）
- 社区页：查询时按 `category` 过滤

### 决策 6：AI 积分提示数据源

积分值 X 由 `ApiClient`（业务后端）接口返回，前端不写死。`aiConsultBaseUrl` 前缀匹配的 AI 接口已有统一鉴权（`x-api-key`/`x-timestamp`/`x-signature`，见最近提交 `b479a18`/`50985de`），积分提示复用同一数据通道。

## Risks / Trade-offs

- **[风险] PeerApi 接口延期** → "我的宠物"区块阶段 1 显示"-"而非真实状态，体验降级但不阻塞上线；阶段 3 是插槽式接入，延期只影响状态展示完整度。
- **[风险] 业务后端事件表/接口延期** → 系统通知列表页先 mock，等接口好了接入；极光推送链路现成，推送触达不阻塞。
- **[风险] IM 漫游 7 天误解残留** → 本次设计明确"事件通知不走 IM"，但 `message_page.dart:1197` 的 `fence_alert` 解析仍在。若不清除，未来可能再次被误用为事件通道。**建议**：本轮在 spec 中标注"IM `fence_alert` 解析为历史借用，不作为事件通知设计依据，扩展事件类型应走极光 + 业务后端"。
- **[风险] `coord_transform.dart` 只有 `wgs84ToGcj02`** → 寻宠导航方案 C 两套坐标都在手（`_gcjLatLng` 与 `_position`），不需新增反向转换。但若未来出现"高德返回坐标转回 WGS84"需求，需补 `gcj02ToWgs84`。
- **[取舍] 阶段 1 围栏/低电显示"-"** → 不如真实状态完整，但避免阻塞且不误导用户（优于显示错误的"在围栏内"）。
- **[取舍] 不扩展 IM `fence_alert`** → 牺牲了"会话里也能看告警"的便利，换取事件通知链路单一清晰，长期可维护。

## Migration Plan

本变更为纯前端重构 + 后端接口对接，无数据迁移。部署顺序：

1. **纯前端改动**（无依赖，可先行）：文案修复、AI 积分提示、项圈页/安全设置页精简、我的页铃铛修复、社区分类联动、寻宠导航、启动页品牌名。
2. **前端 + 现成数据**：首页账号展示位、签到卡片、AI 健康顾问卡片、消息页系统通知卡片（mock）、系统通知列表页（mock）。
3. **后端接口就绪后接入**：系统通知列表页真实数据、已读回写。
4. **PeerApi 接口就绪后接入**：首页"我的宠物"围栏/低电状态。

**回滚策略**：各 capability 独立，可单独回滚。系统通知列表页在接口未就绪时返回 mock，不影响其他页面。

## Open Questions

- **`_EmotionBadge` / `_EmotionAdviceBanner` 去留**：`PetMoodSection` 现承载"宠物档案展示"与"AI 情绪结果展示"两个职责。改造为"我的宠物"区块时，AI 情绪结果展示是删除、搬到 AI 解析区、还是保留？不阻塞架构，做首页时再定。
- **"健康数据 ›"入口是否预留**：健康报告页依赖项圈行为分析模型（本轮暂不处理）。入口做"预留（点了提示即将上线）"还是干脆不做？做首页时再定。
- **业务后端 `t_fence_alert` 表是否在用**：表已建但 grep 未见写入调用方，可能是空壳表。不影响前端（前端调查询接口而非直接读表），但影响后端工作量评估。
- **极光推送发送端归属**：是 PeerApi 直接调极光 REST，还是 PeerApi → 业务后端 → 极光？前端不关心（发送端不在前端），但影响后端分工。
