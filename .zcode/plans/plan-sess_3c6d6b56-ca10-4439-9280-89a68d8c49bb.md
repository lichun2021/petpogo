## 实施方案

### 1. 为宠物分享增加专用接收流程

当前 `ShareLandingPage` 只处理 `device`，`pet` 被错误分发到普通 `_ResultCard`，因此只有“回到首页”，不会调用接受接口。

改为按分享类型分发：

```text
device → _DeviceShareCard
pet    → _PetShareCard
其他   → _ResultCard
```

`_PetShareCard` 从 resolve payload 读取：

- `order`：Peer 接受分享必需口令
- `petId`：Peer 宠物 ID
- `petName`：宠物名称
- `imageUrl`：宠物头像

`order` 缺失时显示“邀请信息不完整”，禁用接受，不发送请求。

### 2. 调用真实宠物接受接口

点击主按钮后明确显示确认语义：

```text
同意并接受宠物邀请
```

确认后调用已有：

```dart
petShareRepositoryProvider.acceptShare(order)
```

对应：

```text
POST https://peer.jxpetai.com/pet/share/accept
Content-Type: application/x-www-form-urlencoded
Body: order=...
```

通话、设备或业务后台接口不参与宠物接受；Peer 是成员关系的事实来源。

接受期间：

- 按钮显示“正在接受…”和进度；
- 禁止重复提交；
- 不依赖 Toast 作为唯一状态。

### 3. 重做宠物邀请卡 UI

将截图中的普通分享结果卡改成明确的邀请决策卡：

1. 宠物头像或宠物图标；
2. 标签“宠物共享邀请”；
3. 标题“邀请你共同管理「宠物名」”；
4. 说明“接受后可在我的宠物中查看并共同管理”；
5. 权限信息：
   - 身份：共享成员；
   - 可查看宠物资料及关联信息；
   - 不改变宠物所有权；
6. 24 小时有效期或服务端 `expiresAt`；
7. 主按钮“接受宠物邀请”；
8. 次级按钮“暂不接受”。

页面改为可滚动布局，减少截图中上下大量空白，并适配小屏、大字体和安全区。

### 4. 完整页面状态

宠物邀请卡维护明确状态：

- `ready`：等待用户确认；
- `accepting`：正在接受；
- `accepted`：接受成功；
- `alreadyMember`：重复接受或已经加入；
- `owner`：分享创建者自己打开；
- `expired`：邀请已过期；
- `failed`：接受失败，可重试。

具体行为：

- `createdByCurrentUser == true`：显示“这是你发出的宠物邀请”，不显示接受按钮；
- `expiresAt <= now`：显示“邀请已失效”，不调用 accept；
- 接受失败显示页面内错误和“重新接受”，不只弹 Toast；
- Peer 返回“已接受/已经是成员”时按幂等成功展示；
- 成功后不立即自动跳转，先展示稳定成功页，让用户主动选择“查看我的宠物”。

### 5. 接受成功后刷新正确的数据源

宠物分享和宠物列表均使用 Peer 数据：

- accept：`/pet/share/accept`
- 我的宠物：`/pet/info/list`

当前 `petControllerProvider` 使用的是业务后端 `/sdkapi/pet/list`，不能用它刷新 Peer 共享宠物。

因此：

- 为 `PetListPage` 注册正式 GoRouter 路由；
- 接受成功后用户点击“查看我的宠物”进入新的 `PetListPage`；
- 新页面的 `initState` 自动重新请求 `/pet/info/list`，确保显示刚接受的共享宠物；
- 不直接跳当前静态 `PetDetailPage`，因为它尚未按 Peer petId 加载真实宠物数据。

涉及：

- `app_routes.dart`
- `app_router.dart`
- `pet_list_page.dart`
- `share_landing_page.dart`

### 6. 修复未登录后的邀请回跳

当前未登录用户从分享页点击“去登录”后，登录成功会固定回首页，丢失分享 code。

增加：

```text
/login?returnTo=<完整分享路由>
```

流程：

1. 分享页构造当前 `/share?code=...&type=pet`；
2. 点击“登录并继续”进入带 `returnTo` 的登录地址；
3. 登录成功后由现有 GoRouter guard 读取并验证 `returnTo`；
4. 只允许返回合法内部 `/share` 路由且 code 非空；
5. 回到原分享页后自动 resolve，再展示接受按钮；
6. 普通登录没有 `returnTo` 时仍回首页。

不使用任意外部 return URL，避免开放重定向和导航循环。

### 7. 设备分享回归保护

本轮不改设备接口，但会确保：

- `device` 仍调用 `/user/device/accept`；
- `pet` 只调用 `/pet/share/accept`；
- 普通位置、抓拍、打招呼分享仍使用通用结果卡；
- owner、过期、错误等通用信息不破坏设备流程。

### 8. 后台契约确认

业务后台 resolve 需要原样返回：

```json
{
  "type": "pet",
  "payload": {
    "order": "...",
    "petId": "...",
    "petName": "..."
  }
}
```

本地后台当前已有宠物 payload 直供改动，但尚未提交。App 实现会按上述契约读取；后台上线前需要确保该改动已部署，否则 create 阶段仍可能查询本地 `t_pet` 返回 404。

本轮不新增业务后台 accept/consume 接口，因为真实宠物成员关系由 Peer 管理。

### 9. 测试与验证

新增或更新测试覆盖：

- `type=pet` 分发到宠物邀请卡；
- payload order 正确传给 `PetShareRepository.acceptShare`；
- payload 缺 order 时不发请求；
- owner 自己打开时不显示接受按钮；
- 过期邀请不可接受；
- 接受中禁止重复提交；
- 接受成功显示稳定成功态和“查看我的宠物”；
- 接受失败可重试；
- 登录 `returnTo` 嵌套编码、合法校验和登录后回同一 code/type；
- 普通登录仍回首页；
- device 分享流程不变。
